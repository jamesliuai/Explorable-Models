# Policy-scoped activity tools

Status: implementation guide for `@explorable-models/agent` activity tools (report §5.3, §6.2, §7.3, §8.6, §15.1, §15.3,
§16; ledger A21 tool channel, A55, A57). Source: `packages/agent/src/activity-tools.ts` and
`packages/agent/src/activity-relay.ts`. Published schemas: [`activity-tool-schemas.json`](activity-tool-schemas.json)
(generated by `scripts/generate-api.mjs`; a test fails when it drifts from the runtime descriptors).

The tools let a tutor agent work with one host-authorized activity. They are task-oriented, compact and bounded by
host policy. They do not replace the lower-level document tools (`visualization_*`), which remain available only for
approved exploratory composition and authoring.

## 1 Scope model

The host builds one tool set per authorized context. Nothing in tool input can change it.

| Context field | Meaning |
| --- | --- |
| `adapter`, `catalog` | The `StudyHarnessAdapter` and the installed catalogue it was constructed with |
| `policy()` | The host's current policy for the activity (for example `HostPort.getPolicy`) |
| `hostSessionId`, `activityId` | The one session and activity this tool set may touch |
| `policyRevision` | The policy revision the host authorized; any other current revision makes every call `STALE_POLICY_REVISION` |
| `audience` | `learner-visible`, `tutor` or `teacher`; decides inspection depth, summary audience and sampling |
| `allowedOperations` | Host grant. Effective operations = grant ∩ `policy.allowedTools` (∩ `independentTask.permittedTools` while independent work is active) |
| `binding` / `host` | The tutor binding (`prepared.binding('tutor', …)`) and, optionally, host routing for reveal, save and close |
| `lifecycle` | Host hooks for prepare and restore: host-owned request fields, binding of new activities, artifact lookup by ID |
| `composition` | Optional document tools for exploratory composition (only with policy mode `exploratory`) |

Rules the executors enforce (tested in `tests/agent/activity-tools.test.ts`):

- **Authority comes from the binding.** Input schemas reject unknown fields. Fields such as `actor`, `origin`,
  `principal`, `sessionId`, `hostSessionId`, `activityId`, `policy`, `review` or `lifecycle` are rejected with a
  repair hint saying that authority comes from the host binding. Events show actor `tutor` because the binding is a
  tutor binding.
- **Guards are not permissions.** `expected` carries the revisions copied from `activity_inspect`. A stale guard fails
  (`STALE_MODEL_REVISION`, `STALE_PRESENTATION_REVISION`, `STALE_ACTIVITY_REVISION`); a current guard grants nothing.
- **Recheck after every await.** Each executor reads the host policy and checks the revision, standing, session,
  activity presence and operations before it starts, after each await, and immediately before its commit. A commit is
  never undone: if the policy changed while it ran, the result says `authorization: { current: false }` and later
  calls fail until the host binds a new tool set.
- **Standing by host time.** Standing is judged by host time, not by the policy's own issue time: the executor asks the
  adapter (`adapter.policyStanding(policy)`, the adapter's host clock — the latest policy, receipt or acknowledgement
  timestamp it has observed), and a bound activity's own standing (`AudienceState.standing`: a host revocation, a
  catalogue revocation or an expiry its acknowledgements showed) refuses every step too. Once the policy has expired
  every tool fails with `POLICY_EXPIRED` — read-only ones included (`activity_inspect` in both views,
  `activity_summarize`, `activity_describe_template`, `activity_discover`), with or without an open activity — exactly
  like commands and sampling (`tests/agent/activity-tools-standing.test.ts`). `createActivityTools` throws a
  `TypeError` naming `adapter.policyStanding` when the adapter it is given lacks it, so a host that wraps or proxies the
  adapter must forward that method; the tools never run without the host-time check.
- **Declared scope equals runtime scope (A55).** Every descriptor has `scope.operations`, `scope.variants` (per action,
  view or proposal kind), `scope.audiences`, `scope.hostRoute` and `scope.activity`. Removing any declared operation
  from the grant or from the policy makes the call fail with `POLICY_DENIED` before any effect.

| Tool | Operations | Audiences | Host route | Notes |
| --- | --- | --- | --- | --- |
| `activity_discover` | `discover` | all | — | Approved exact versions, controls, lifecycle, review scope, unsupported capabilities with alternatives |
| `activity_describe_template` | `discover` | all | — | On-demand detail; equations, constraints and assumptions only for teacher / tutor with full inspection |
| `activity_prepare` | `prepare` | all | — | Host lifecycle hook; parameters ⊆ `policy.permittedControls` |
| `activity_inspect` | `inspect.learner` / `inspect.tutor` / `inspect.teacher` | all; `full` not for learner-visible | — | Learner view is exactly the learner projection |
| `activity_propose_revision` | `propose-revision` (+ `compose.exploratory`) | all | — | Checks without applying; exploratory candidates labelled "exploratory, not reviewed" |
| `activity_request_reveal` | `request-reveal` | all | yes | Returns `authorized`, `pending` or `denied`; the host decides |
| `activity_operate` | `operate.parameters` / `.navigation` / `.playback` / `.presentation` | all | — | Per action |
| `activity_summarize` | `summarize` | all | — | Audience-filtered deterministic summary |
| `activity_save` | `save` | all | yes | Returns a reference; the artifact stays in host storage |
| `activity_restore` | `restore` | all | — | Artifact ID resolved by the host (never a path or URL) |
| `activity_close` | `close` | all | yes | Fixed close reasons |
| `activity_sample` | `sample` | teacher | — | `policy.sampling.allowed` and `policy.inspection.teacher`; never cached |

## 2 Results and disclosure

Every result is `{ ok: true, data, scope }` or `{ ok: false, diagnostics }`. `scope` keeps three statements apart:

```json
{
  "validation": { "kind": "technical", "checks": ["schema", "guards", "host-policy", "parameter-constraints"], "meaning": "Technical checks only …; they are not scientific or subject review." },
  "review": { "lifecycle": "reference-checked", "scope": "no independent subject review" },
  "activity": { "activityId": "act-1", "stage": "explore-step", "context": "instructional", "mode": "approved", "closed": false, "persistence": "saved", "ui": "ready" }
}
```

- Mutating tools (they take an `operationId`) return only learner-visible data — the learner projection, guards,
  verdicts and artifact references — so the operation receipt cache —
  keyed by `operationId` and an argument fingerprint — never holds teacher-only data. Repeating an `operationId` with
  the same arguments returns the original result; changed arguments fail with `OPERATION_CONFLICT`.
- Full scientific state comes only from `activity_inspect` with `view: "full"` (teacher with
  `policy.inspection.teacher`, or tutor with `policy.inspection.tutor = "full"`) and from `activity_sample`. Neither is
  cached by the tools or by the relay.
- Diagnostics use a fixed vocabulary (`ACTIVITY_TOOL_MESSAGES`, `ACTIVITY_TOOL_REASONS`); paths name only the caller's
  own input fields. No message is built from content. The only exception is `detail` on errors about an exploratory
  document the agent wrote itself.

## 3 Small examples

Host construction (host code, never model output):

```ts
import { createActivityTools } from '@explorable-models/agent';

const tools = createActivityTools({
  adapter, catalog, policy: () => hostPort.getPolicy({ activityId }),
  hostSessionId, activityId, policyRevision: policy.revision, audience: 'tutor',
  allowedOperations: ['discover', 'prepare', 'inspect.learner', 'propose-revision', 'request-reveal', 'operate.parameters',
    'operate.navigation', 'operate.playback', 'operate.presentation', 'summarize', 'save', 'restore', 'close'],
  lifecycle: {
    request: () => ({ objectiveIds, hostSessionRevision }),
    bind: prepared => { mountLearnerSurface(prepared); return { binding: prepared.binding('tutor', 'tutor-tools'), host: prepared.host }; },
    loadArtifact: artifactId => artifactStore.get(artifactId),
  },
});
```

Agent calls (JSON):

```json
{ "tool": "activity_prepare", "input": { "operationId": "op-1", "template": { "templateId": "quadratic-gradient-descent", "version": "1.0.0" }, "parameters": { "x0": -6 } } }
{ "tool": "activity_inspect", "input": {} }
{ "tool": "activity_request_reveal", "input": { "operationId": "op-2", "target": { "kind": "stage", "toStage": "explore-step" }, "expected": { "activityRevision": 0, "policyRevision": 1 } } }
{ "tool": "activity_operate", "input": { "action": "commit-parameters", "operationId": "op-3", "values": { "eta": 0.75 }, "expected": { "scientificVersion": 1, "runId": "…", "activityRevision": 1, "policyRevision": 1, "presentationRevision": 0 } } }
```

Copy `expected` from the latest `activity_inspect` or mutating result whole; every field given is checked.

## 4 Repair cases

| Failure | Meaning | Repair (never bypass a guard) |
| --- | --- | --- |
| `INVALID_INPUT` at `$.actor` (authority field) | Input tried to claim authority | Remove the field |
| `POLICY_DENIED` at `$.parameters.a` (personalisation) | Parameter not personalisable | Use controls marked `personalisable` |
| `OUT_OF_DOMAIN` at `$.values.eta` | Outside the control range | Choose a value inside `min`/`max` from `activity_inspect` |
| `CONSTRAINT_VIOLATION` | Coupled limit violated | Choose another combination; nothing changed |
| `POLICY_DENIED` at `$.values.eta` while predicting | Control fixed in this stage | `activity_propose_revision` with `kind: "stage"`, then `activity_request_reveal` |
| `STALE_MODEL_REVISION` / `STALE_ACTIVITY_REVISION` | State moved | `activity_inspect`, retry with a new `operationId` |
| `STALE_POLICY_REVISION` (no path) | The tool set is no longer authorized | Stop; the host must bind a new tool set |
| reveal `status: "pending"` | The host did not record the authorization; nothing shown | Retry later with the **same** `operationId` (the same request is resent) |
| reveal `status: "denied"` | Stage or policy does not permit it | Do not retry; continue with what is shown |
| `OPERATION_CONFLICT` | `operationId` reused with other arguments | New `operationId` |
| `INVALID_REFERENCE` for a template, or an unsupported request ("plot a general ODE") | Not installed | Decline and offer the alternative from `activity_discover.unsupported` |

## 5 Reveal, sampling and exploratory composition

- `activity_request_reveal` routes through the host control with actor `tutor`; the host's `HostPort` issues (or
  refuses) the receipt. `authorized` means the host persisted the exposure intent, not that the learner saw it; the
  learner surface acknowledges display. A host refusal under the HostPort convention
  ([activity-runtime §10](activity-runtime.md#10-host-refusals-and-persistence-failures-63-72): `POLICY_DENIED`,
  `POLICY_EXPIRED`, `CONTENT_REVOKED`, `STALE_POLICY_REVISION`, `INVALID_INPUT`) is reported as `denied` with that code
  and is never resent; any other host failure is `pending` (`PERSISTENCE_FAILED`) and the same `operationId` resends it.
  `denied` also comes from the tool's own policy recheck and from the adapter's stage, policy, independent-context or
  receipt checks.
- `activity_sample` evaluates the exact installed model in an isolated worker request for teacher contexts. The
  learner run, preview, selection, playback and journal are unchanged.
- Exploratory composition requires policy mode `exploratory`, `exploratory.allowed`, the `compose.exploratory`
  operation and host-supplied document tools. Text with markup, resource URLs or definitional/resource TeX commands is
  rejected before the document tools see it; a document may not use an installed template's ID; a forged
  `provenance.review` is rejected by the document schema. Candidates are returned with `label: "exploratory, not
  reviewed"` and are never committed by these tools.

## 6 Relay

`createActivityRelay` / `createActivityToolEndpoint` carry the same tools between the host (where the agent runs) and
the learner WebView (where the adapter runs). The host authenticates the principal and binds it to one host session
and activity (`connect`); `dispatch` refuses unbound principal/session/activity triples (forged principals, other
sessions, cross-activity calls), expired bindings and arguments that name a principal, session, activity or review
status. The relay keeps operation identity per binding across reconnects: an identical retry of an operation whose
result it received returns that result without a second call, and changed arguments fail with `OPERATION_CONFLICT`.
A reply that arrives after its request was cancelled is still recorded, so cancellation after commit returns the
committed result. Tests: `tests/agent/activity-relay.test.ts`.

## 7 Evidence and the real-host trial

`tests/agent/activity-trial.test.ts` runs the G3 sequence with a deterministic, rule-based caller over the relay
against the fixture host. It is protocol evidence only: **it is not an LLM trial and does not satisfy A57.** The real
configured host-agent trial follows [external-gates.md § G3](external-gates.md#g3-real-configured-host-agent-trial-a57)
with the actual Study Harness agent path, owner-supplied credentials, a pinned model configuration and a budget, and
records sanitized identifiers, tool names, outcomes and repairs. Until that is done, A57 remains open.

### 7.1 Opt-in trial recorder

`createTrialRecorder` (`@explorable-models/agent`, `packages/agent/src/trial-recorder.ts`) records such a trial. The host
creates it only for a trial it runs on purpose and wraps the relay it already uses:

```ts
const recorder = createTrialRecorder({
  trialId: 'g3-2026-11-02-1', kind: 'real-agent-trial',
  configuration: { provider: 'host-provider-adapter', model: 'pinned-model-id', settings: { temperature: 0 } },
  budget: { maxRequests: 60, maxInputTokens: 400_000, maxCost: { amount: 5, currency: 'USD' } },
  host: { name: 'study-harness', commit, binarySha256, platform: 'macos-arm64' },
});
const relay = recorder.relay(createActivityRelay({ authorize }));   // dispatch results are recorded
recorder.markStep(requestId, 'host-reveal');                        // G3 step evidenced by a request
recorder.noteRepair(repairRequestId, 'adjust-value', rejectedRequestId);
recorder.noteUsage(requestId, { inputTokens, outputTokens, cost });  // host-measured numbers only
const record = recorder.record();                                   // study-harness.agent-trial-record/1
```

| Kept | Never kept |
| --- | --- |
| request IDs (an invalid or reused ID becomes `invalid-N` / `duplicate-N`), tool names (`unknown` outside the twelve), outcome as `ok` with a status word, diagnostic codes, or the relay error code | tool inputs and results, diagnostic messages and paths, learner or study text, prompts, model output |
| a salted `sha256:` digest of each operationId (retries of one operation stay correlated) | the operationId itself |
| G3 step marks and repairs from fixed vocabularies (`G3_STEPS`, `TRIAL_REPAIRS`) | free-text notes |
| provider and pinned model identifiers, a digest of the configuration, the budget and numeric usage totals with `withinBudget` | keys, tokens and other credentials: a setting whose name or value looks like one is refused (`TypeError`), not digested |

The record is bounded (`TRIAL_LIMITS.entries`, then `truncated: true` with the totals still counted) and validates
against `AGENT_TRIAL_RECORD_SCHEMA`, published as
[`templates/agent-trial-record.schema.json`](templates/agent-trial-record.schema.json); fill
[`templates/agent-trial-log.md`](templates/agent-trial-log.md) beside it. `kind` is the host's statement: only a run
through the actual Study Harness agent path is `real-agent-trial`; scripted callers, mock transports and fixture hosts
are `scripted-fixture`. The recorder never sends the record anywhere. Tests: `tests/agent/trial-recorder.test.ts`
(redaction against the real relay, with records labelled `scripted-fixture`).

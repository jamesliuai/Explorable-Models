## 1 Scope

- **One desktop machine** (Apple M3, 8 cores, 16 GiB, macOS 26.6), **Chromium** through Playwright (headless shell 156,
  WebGL through ANGLE/Metal on the M3 GPU), the **production** build of the packed consumer
  (`examples/study-harness-consumer`) served with the production CSP. The spatial workloads are also run once on
  software WebGL (SwiftShader, the default of Playwright's headless shell) and reported separately.
- This benchmark drives Chromium only. The packaged reference host's WKWebView is measured separately, against the
  same targets, by the packaged conformance run's `performance` chain (§3a, [native.md](native.md)). **Not**
  Firefox/WebKit, **not** a low-end or mobile device, **not** the Study Harness application.
- Each run records the macOS console lock state as measured (`ioreg`, at the start and the end of the run; `null` when
  it cannot be read). Headless Chromium renders offscreen, so the lock state does not hide these pages; the cited run
  recorded the session unlocked at both points.
- The host in these measurements is an in-memory fixture (`examples/study-harness-consumer/src/host.ts`) with
  controllable latency. Storage acknowledgement is therefore the fixture's own latency plus the adapter's journal path;
  a real host's store adds its own cost, which these numbers do not include. Provider latency is **not applicable**:
  no slider movement, frame, camera change, commit or reveal on these paths calls a provider.
- The machine was shared with other development work during the runs; the load average at start and end of each run is
  recorded in the evidence. Isolated maxima can come from outside the page.
- **Host-level targets are not library guarantees.** The report's 3-second cached launch and approximately 250 MB idle /
  500 MB ordinary-study memory targets concern the whole Study Harness application; this library neither measures nor
  guarantees them. The JS-heap samples below are page diagnostics, not process memory.
- Automated measurements are engineering evidence. They are not scientific review, accessibility certification or
  evidence of learning benefit.

## 2 Method

**Packed consumer** (`verify-consumer.mjs`). `scripts/study-harness/pack.mjs` builds and packs all six packages; the
tarballs are copied out and checked against the pack manifest's sha256 and integrity; `examples/study-harness-consumer`
and `examples/consumer` are copied into a fresh temporary directory and installed from the tarballs with an empty,
isolated npm cache, `--ignore-scripts`, pinned `react`/`react-dom`/`three`/`vite`/`typescript`/`@types/*` and no
aliases (every `@explorable-models/*` directory must be an extracted tarball whose lockfile integrity equals the manifest's).
Then: every public entry is imported in plain Node with no DOM globals (`@explorable-models/core`, `/model`,
`/declarative`, `activity`, `catalog`, `player`, `player/activity`, `player-3d`, `agent`; the two worker entries start a
worker loop on import and are browser-only); `tsc` checks the consumer against the packed declarations with
`skipLibCheck: false`; Vite builds the four pages together (served to the browser) and each budgeted page alone
(measured). The build keeps hidden source maps so every emitted byte can be attributed to a package. The consumer
and packaged reference host use native ESM loading without Vite's optional module-preload hints; the audit still
counts every static dependency and worker, whether or not a preload tag is present.

**Budgets.** The exact rules are in [budgets.json](budgets.json). In short: the existing 2D consumer is the sum of
default-level gzip over all emitted JS (the rule `verify-packages.mjs` has always used); the activity entry is the sum of
level-9 gzip over every `.js` file statically reachable from the entry HTML — script and modulepreload tags, their
static imports (an esbuild metafile of the emitted files) and every `.js` file referenced with
`new URL(…, import.meta.url)` from them (the kernel worker) — excluding `import()` targets, which are budgeted as lazy
assets. The eager graph must contain no source from Three.js, player-3d, KaTeX, Playwright, the MCP SDK, provider SDKs,
Tauri, the CLI or the agent package (checked through the source maps and by text markers), and no inline script.

Capture serialization/font embedding/PNG rasterization and the saved-record migration reader/codec are loaded by their existing asynchronous capture/restore operations. Public synchronous capture helpers and `migrateArtifact` retain their APIs. Policy and committed-frame checks remain eager; a capture whose content or revisions change while its renderer loads is refused, while a persistence-only status update can settle. The optional KaTeX font URL table is likewise loaded only when visible math requests bundled fonts. Their emitted raw/gzip bytes are listed under `lazy.other` in consumer evidence, so the distribution cost remains visible. This uses the existing dynamic-import traversal rule and unchanged 250,000 B ceiling.

**Browser flows under CSP.** Every response carries `default-src 'none'; script-src 'self'; style-src 'self'; img-src
'self' blob:; font-src 'self'; connect-src 'self'; worker-src 'self'`. CSP violations are collected with a
`securitypolicyviolation` listener installed before any page script and from the console (which also carries worker
messages); console errors, page errors and failed requests fail the check. A separate context runs intended negative
probes (an inserted inline script, a parsed style attribute, a `data:` image) to show that the policy is enforced
(DevTools evaluation is exempt from the eval check, so `new Function` is not a valid probe).

**Benchmark** (`benchmark.mjs`, page `bench.html`). Measurements are taken in the page with `performance.now()`:

| Measure | From | To |
| --- | --- | --- |
| Input feedback acknowledgement | `input` event `timeStamp` of a real pointer drag (Playwright mouse at a 60 Hz pacing) | paint of the first frame whose control output shows that value or a later one |
| Preview frame rate | requestAnimationFrame cadence between the first and last input | dropped frames = Σ(round(Δ/refresh) − 1) against the idle refresh interval; tentative-frame rate = changes of the painted tentative frame per second |
| Commit → visible frame | learner-binding command call | paint (rAF, then a task) of the first frame whose DOM (`data-ema-projection`) shows the projection with the new committed frame |
| Components | worker: `evaluate` postMessage → reply (catalogue worker wrapped for timing); render: projection publication → DOM commit; paint: DOM commit → paint | storage: first journal append after the command → host acknowledgement |
| Spatial | command or pointer move | the renderer's frame counter (`player-3d` `inspect`) increments, then paint |

Each series discards warmups and reports nearest-rank p50/p95/max with the sample count. Resource counts come from an
init script that wraps `Worker`, timers, intervals, animation frames, `window`/`document`/`MediaQueryList` listeners and
`attachShadow`, labelled by phase. The 100-cycle lifecycle stress starts after one warm-up cycle, because React DOM
registers its per-document listeners once, on the first root of a document, and never removes them; they belong to the
page, not to an activity.

**Outcome and evidence** (`scripts/study-harness/benchmark-evidence.mjs`). Every row the benchmark records is
required (`REQUIRED_TARGET_KEYS`): the input-feedback, preview and small-2D commit rows, the larger workloads, each
spatial activity's rows, rapid inputs, offscreen, the lifecycle stress and stalled persistence. The spatial rows are
the pointer-orbit input target and three reported-only measures per activity: commit → renderer frame and camera
command → renderer frame on the GPU, and commit → renderer frame on software WebGL. A reported-only measure has no §18
number and is never judged against one, but it is required like a target. A workload that throws, a series without
samples or a missing result never removes a row, whether the row carries a target or is reported only: the row stays
in the evidence as "not measured" with `met: false`, it is listed under Errors in `evidence/performance.md` (with the
workload's error when the workload threw), and the run exits 1, as it does for a missed target, a console or page
error, a failed request or a CSP violation. The lifecycle row is met only with the 100 cycles of `budgets.json`; a
`--quick` run reports fewer cycles as "not run (quick run)" and is never release evidence. Two machine conditions are
environment gaps, "not run (environment)" with exit 2, to resolve or report and never a pass: a GPU run without
hardware WebGL (no WebGL 2 context, or a software rasterizer such as SwiftShader) for the GPU spatial rows, and a
software-WebGL run with no WebGL 2 context at all for the software rows. A spatial renderer that is not ready although
its run has the WebGL it needs (hardware WebGL for the GPU run, any WebGL 2 context for the software run) fails.
`performance.json` records the source commit and dirty flag, the package-lock sha256, Node, the tool versions and the
pack the measured consumer was built from, and every run, a failed one or one that throws included, is also written to
`evidence/history/performance-<time>.json`.
Every recorded commit failure and any unacknowledged input in the hardware-GPU orbit target fail the benchmark; software-WebGL orbit latency remains reported-only. The release pipeline's `benchmark` gate recomputes target statuses from raw results and current budgets, and refuses inconsistent persisted statuses with the same rules
([release.md](../release.md)).

### 3b Supported packaged drag scope (2026-10-28)

The supported target for the ordinary quadratic drag in the macOS reference host is **30 fps**, with tentative
frames keeping up with at least 90% of the lesser of the measured input and display rates. **60 fps remains an
improvement objective and is not established for this packaged path.** This is the explicit scope decision permitted
by report §18, recorded in `budgets.json` as `preview2d.packagedSupportedFps` and architecture D14. It leaves the
existing usable floor, input acknowledgement, 100 ms commit limit, dependency ceilings and scientific checks intact.

Two full packaged runs measured 56.03 fps (`full-2026-10-27T04:20:05.108Z`) and 58.56 fps
(`full-2026-10-27T07:14:12.490Z`, 32 dropped of 695 frames). Those measurements establish usable interaction on this
machine, with occasional missed display frames, and do not establish a stable 60 fps path. The fixture includes
linked math and trace rendering, retained host records, and durable native persistence. These are workload facts,
not a diagnosis of the missed frames: a causal profile and further optimization are deferred. Exact entry remains
available. The next packaged run must still measure actual frame rate, dropped frames and input cadence, fail below
the supported target, and report the 60 fps objective separately. This decision does not extend support to other
platforms or change the separate Chromium benchmark's objective.

## 4 Findings and their causes

The findings were reported with evidence for the owners of the packages named. F1–F5 have since been fixed in those
packages (catalogue, core model, activity, player); their entries record the cause, the fix and the new measurement.
No test was removed and no budget was revised to hide a finding.

**F1 — The activity entry exceeded its 250,000-byte ceiling (resolved: fixed, not re-budgeted).** Phase 4a measured
281,836 B (plain DOM) and 280,246 B (React). The main chunk was 854,117 B (251,283 B gzip) and the kernel worker
93,985 B (30,553 B gzip). The estimated gzip shares of the causes, inside the main chunk, were: catalogue content
36.7 KB, catalogue kernels on the main thread 10.2 KB (also shipped in the worker) and the schema 2.0 document compiler
9.1 KB. The fix removed each cause; the rules and the ceiling are unchanged (`budgets.json`, D14).

- **Content per template on demand.** `createLazyCatalog` (`packages/catalog/src/lazy.ts`) keeps only the generated
  installed index eager: references, model identities, reference-suite digests, kernel identities and discovery
  entries, about 3.6 KB gzip. The review registry, revocations and deprecations are eager too. Each template's
  content (template, learner copy, manifest) is one chunk fetched by `load()`. The adapter calls `load()` in
  `validate`, `prepare` and `restore` (`ActivityCatalog.load`). Loaded content is served only if it reproduces the
  installed digests and passes the eager catalogue's validation; otherwise it is withdrawn with `INTEGRITY_FAILURE`.
  `getCapabilities()` lists every template before any content loads (`ActivityCatalog.describe`).
  `createInstalledCatalog` is unchanged for tooling and tests.
- **Kernel code only in the worker, per kernel.** The catalogue worker serves `INSTALLED_KERNEL_SOURCE`, the installed
  identities with a loader per kernel. Each kernel's module is imported in the worker the first time a request names
  it. The main thread carries no kernel code. Content chunks keep only the constants that templates and manifests
  reuse (IDs, versions, domains; 251–574 B each), because the kernel objects are marked pure.
- **Document compiler out of the kernel-only path.** Schema 2.0 document execution is opt-in
  (`enableDocumentExecution()` in `@explorable-models/core/model`). Without it, a document-kind manifest is refused with
  `UNSUPPORTED_CAPABILITY`. Neither the page nor the catalogue worker bundles the compiler or interpreter
  (`tests/core/document-execution.test.ts` bundles the kernel-only API and checks this).

Result (`verify-consumer.mjs`, same rules, the consumer run cited in §3): **247,861 B** plain DOM and **246,415 B** React, 2,139 B and 3,585 B under the ceiling. The eager graph holds the main chunk (230,764 B gzip) and the kernel worker (17,097 B gzip). It carries 0 B of catalogue content and 0 B of kernel code. All five templates' content, 159,584 B raw, sits in five lazy chunks of 24,668–37,837 B (7,160–10,925 B gzip). The plain-DOM and React flows fetch only the quadratic content chunk, after
the page is ready. The margin is small: other work in this phase grew the activity runtime and the learner surface by
about 20 KB gzip, so further growth will need the same treatment rather than a new ceiling.

**F2 — More than 64 synchronous preview updates in one task left the tentative frame at the 64th value until commit
(resolved).** Phase 4a measured that bursts of 65 or more synchronous `updatePreview` calls stopped the painted tentative
frame at update 64 while every call returned `ok`. Cause: `createModelSession` registers an idempotency receipt per
`previewParameters` call and refuses with `RESOURCE_LIMIT` once `MODEL_SESSION_LIMITS.deduplicatedOperations` (64)
receipts are pending (`packages/core/src/model/session.ts`, `receipt()`), and every call of the burst reached the
session. The controller now keeps one preview evaluation in flight plus the newest pending value
(`packages/activity/src/controller.ts`, `updatePreview`); a value replaced before it was sent is coalesced and never
sent, so a burst cannot reach the session's bound. In the cited run 6 bursts of 60 and 3 bursts of 200 calls painted the newest value every time, with 2 worker messages per preview and 0 refused updates, and each commit applied the
newest value.

**F3 — A host step during stalled persistence waited about 15 s before it was refused (resolved: about 1 s).** With
journal appends held, a stage transition used to resolve with `PERSISTENCE_PENDING` only after 14.6 s, because
`flushFirst()` (`packages/activity/src/controller.ts`) waited for the in-flight append until the host call timeout
(`DEFAULT_HOST_TIMEOUT_MS` = 15,000 ms, `packages/activity/src/journal.ts`). Flush-first steps now wait at most the
adapter option `persistenceWaitMs` (0–60,000 ms, default 1,000 ms) and then fail with `PERSISTENCE_PENDING`; the host
repeats the step with the same `operationId` once the journal drains. Re-measured with the benchmark page's own
`stalledPersistence` scenario on the production packed consumer under the production CSP (Chromium 156, Apple M3,
8 runs after one discarded warmup, default `persistenceWaitMs`, outbox limit 24;
`node scripts/study-harness/measure-stalled-persistence.mjs`, evidence
[stalled-persistence.json](evidence/stalled-persistence.json)): the stage transition was refused with
`PERSISTENCE_PENDING` after p50 1,003 ms, p95 1,006 ms (max 1,006 ms). In the same runs 21 commits rendered before the
22nd was refused with `PERSISTENCE_BACKPRESSURE`, a layout change still rendered (p50 10.4 ms, p95 23.4 ms), the chip
read “Saving…”, the outbox drained 12.5 ms (p50) after the host resumed and the next commit was accepted. The learner
card keeps working throughout; the host's own control is pending for about one second instead of fifteen.

**F4 — A drag started while the previous release was still committing could jump back while the pointer was held
(resolved).** With worker replies delayed 250 ms and a second drag pressed a few milliseconds after the first release,
Phase 4a saw the slider and output jump from the held pointer value (1.8) to the first drag's committed value (0.6) in
5 of 6 attempts when that commit landed: `ParameterControl`'s `finish()` for the first gesture cleared the newer
gesture's draft. `finish()` now clears the draft only when its gesture is still the current one (the `generation`
guard in `packages/player/src/activity/components/Controls.tsx`). In the cited run the control left the held pointer value in 0 of 6 attempts: it showed 1.8, marked as a preview, while the first commit (0.6) landed, and the release
committed the held value in every attempt.

**F5 — The schema 2.0 document player needed `style-src 'unsafe-inline'` (resolved).** `VisualizationSurface` rendered
an inline `<style>` element, which the production policy blocks. It now adopts its stylesheet as a constructable
stylesheet into the document or shadow root that holds it (`packages/player/src/embedding/stylesheet.ts`, reference
counted per root, one sheet per document). Where constructable stylesheets are missing, it links the packaged
`dist/surface.css`, or `<assetBase>/surface.css` for hosts that rebundle. The benchmark no longer relaxes the policy
for the document-path workloads: they run under the same `style-src 'self'` as everything else, with no violations.
`scripts/verify-packages.mjs` dropped `'unsafe-inline'` from its policy, because the inline style element was its only
reason, and it fails on console errors (a blocked inline style is one). `tests/browser/document-surface-styles.spec.ts`
checks that no style element exists, that the sheet is adopted and shared, and that it is released.

**F6 — Software WebGL.** On SwiftShader the quadratic-surface activity's commit → renderer frame is p95 352.7 ms and pointer-orbit input → frame 166.6 ms (vector orientation 92.9 ms and 34.4 ms); on the M3 GPU the same workloads take 50.1 ms and 31.7 ms. The renderer's resource counts are identical in both cases (7 shader programs, no recompilation per
commit); the difference is rasterization cost. A machine without GPU acceleration should expect the software figures.

## 6 Pools and memory

Bounded pool resources, separate from activity-owned resources: the shared worker budget (at most `maxWorkers` live,
dispose on release — an active, visible card holds one worker; a suspended card holds none; the pool never exceeded one worker in the stress run), adopted stylesheets per shadow root, the lazily loaded KaTeX and renderer modules (one
promise per loader), bundled font registrations, React DOM's per-document listeners, and the fixture host's records
(journal and backup artifacts kept by design). The page JS heap after a forced garbage collection, sampled every ten
cycles, rose from 6.20 MiB to 13.46 MiB over the first 30 cycles (code, compiled functions and caches warming up) and
then stayed between 13.46 and 14.93 MiB over cycles 30–100, while the fixture host's records grew linearly from 0.01 to 1.36 MiB of JSON text. That is consistent with the zero counts above but is not a proof of the absence of leaks: garbage
collection timing and heap accounting are Chromium's. It is not process, worker or GPU memory, and it is not evidence
for the host-level memory targets.

## 7 Revising a budget or target

A ceiling or target changes only with a recorded decision that states the new measurement, the workload, the user
impact and why the cause cannot be fixed; the decision is added to `budgets.json` (`status`, `freeze` fields) and to
[architecture.md](architecture.md) D14. Until then a failing check stays failing: `verify-consumer.mjs` and
`benchmark.mjs` exit non-zero while a budget or target is missed, and `benchmark.mjs` also while a required row, a
reported-only measure included, is missing or not measured (exit 1) or could not run for lack of the WebGL its run
needs (exit 2, §2). F1 was closed by fixing its causes, with no ceiling, rule or target changed (§4).
